## 1. 背景与目标

当前微服务架构中，核心服务（订单、支付、库存）之间的调用链较长（平均深度 5 层）。2024年Q1期间，因下游服务异常导致上游雪崩的事件累计 3 起，平均恢复时间 45 分钟。

**目标**：
- 减少故障影响范围，单服务故障时保证 80% 的基础流量仍可处理
- 提供可观测的熔断/降级指标
- 实现自动化恢复，无需人工介入

## 2. 熔断机制设计

### 2.1 熔断器参数

基于 Netflix Hystrix 语义，我们使用 **Sentinel** 作为熔断实现。核心配置如下：

| 参数                        | 默认值 | 说明                         |
|----------------------------|--------|------------------------------|
| `MIN_REQUEST_AMOUNT`       | 5      | 触发熔断的最小请求数           |
| `ERROR_RATIO_THRESHOLD`    | 0.5    | 错误率阈值（50%）             |
| `SLIDING_WINDOW_SIZE_MS`   | 10000  | 滑动窗口时间（10秒）           |
| `STAT_INTERVAL_MS`         | 1000   | 统计间隔（1秒）               |
| `MAX_RESPONSE_TIME_MS`     | 500    | 最大响应时间阈值（500ms）     |
| `HALF_OPEN_RECOVERY_COUNT` | 3      | 半开状态下允许探测请求数       |

### 2.2 熔断状态机

```
CLOSED -> OPEN（错误率超阈值）
OPEN -> HALF_OPEN（等待 30 秒超时）
HALF_OPEN -> CLOSED（探测请求成功）
HALF_OPEN -> OPEN（探测请求失败）
```

### 2.3 配置示例（YAML）

```yaml
# sentinel-rules.yaml
resources:
  - name: "order-service:createOrder"
    grade: 0  # 错误率
    count: 0.5
    timeWindow: 30  # 熔断时间（秒）
    minRequestAmount: 5
    statIntervalMs: 1000
  - name: "payment-service:processPayment"
    grade: 1  # 响应时间
    count: 500  # 毫秒
    timeWindow: 30
    minRequestAmount: 3
```

### 2.4 熔断恢复策略

- **主动恢复**：HALF_OPEN 状态下，每 2 秒发送 1 个探测请求
- **被动恢复**：若连续 3 次探测成功，自动转为 CLOSED
- **人工恢复**：通过 Sentinel Dashboard 手动重置熔断状态

## 3. 降级策略设计

### 3.1 降级分类

| 降级类型     | 触发条件                     | 降级行为                     |
|--------------|------------------------------|------------------------------|
| 接口降级     | 接口超时或熔断               | 返回缓存数据或空响应         |
| 数据库降级   | 数据库连接池耗尽             | 切换到只读副本或禁用写操作   |
| 缓存降级     | Redis 集群不可用             | 跳过缓存，直接查询数据库     |
| 第三方服务降级 | 外部 API 返回 5xx           | 使用本地 mock 数据           |

### 3.2 接口降级实现

使用 Spring Cloud Circuit Breaker 结合 Resilience4j：

```java
@CircuitBreaker(name = "orderService", fallbackMethod = "fallbackCreateOrder")
@Bulkhead(name = "orderService", type = SEMAPHORE, maxConcurrentCalls = 10)
public Order createOrder(OrderRequest request) {
    return orderClient.createOrder(request);
}

public Order fallbackCreateOrder(OrderRequest request, Throwable t) {
    // 记录降级日志
    log.warn("订单服务熔断，返回默认订单。异常：{}", t.getMessage());
    // 返回缓存的默认订单
    return Order.builder()
        .orderId("DEFAULT-" + System.currentTimeMillis())
        .status("PENDING")
        .amount(BigDecimal.ZERO)
        .build();
}
```

### 3.3 数据库降级

当数据库连接池使用超过 80% 时，自动执行降级：

```yaml
# datasource-degrade.yaml
datasource:
  primary:
    degradeThreshold: 80  # 连接池使用率阈值（%）
    degradeAction: READ_ONLY  # 只读模式
    fallbackDataSource: "read-replica-1"
  replica:
    maxActive: 20
    maxWait: 3000
```

### 3.4 缓存降级

```java
@Cacheable(value = "productCache", unless = "#result == null")
public Product getProduct(Long productId) {
    try {
        return productRepository.findById(productId).orElse(null);
    } catch (RedisException e) {
        // 缓存不可用时降级到数据库
        log.warn("Redis 不可用，直接查询数据库：{}", e.getMessage());
        return productRepository.findById(productId).orElse(null);
    }
}
```

## 5. 验证与测试

### 5.1 单元测试

```java
@Test
public void testCircuitBreakerOpensAfterErrors() {
    // 模拟 5 次请求失败
    for (int i = 0; i < 5; i++) {
        try {
            orderService.createOrder(request);
        } catch (Exception ignored) {}
    }
    // 第6次请求应触发熔断
    Order result = orderService.createOrder(request);
    assertThat(result.getStatus()).isEqualTo("PENDING");
}
```
