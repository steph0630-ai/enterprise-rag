## 1. 总则

### 1.1 目的
为保障研发中心所有业务系统、基础设施、源代码及数据的机密性、完整性和可用性，降低安全风险，特制定本管理制度。本制度适用于研发中心全体正式员工、外包人员及第三方合作人员。

### 1.2 适用范围
本制度覆盖研发中心的所有研发环境（开发、测试、预发布、生产）、代码仓库、CI/CD 流水线、云资源、本地服务器及办公设备。

### 1.3 违规处理
违反本制度者，将依据《员工手册》及《信息安全违规处罚细则》进行通报、绩效扣除或解除劳动合同处理。涉及法律责任的，移交法务部门处理。

## 2. 账号与访问控制

### 2.1 账号管理
- 所有系统（如 GitLab、VPN、云平台、Jira）必须使用个人账号，禁止共享账号。
- 员工入职后，由直属上级在 **24 小时内** 提交账号申请；离职时，HR 需在 **1 小时内** 通知 IT 部门冻结账号。
- 账号密码策略：长度 ≥ 12 位，包含大小写字母、数字和特殊字符。每 **90 天** 强制更换一次。
- 启用多因素认证（MFA），强制绑定至企业微信或 TOTP 应用（如 Google Authenticator）。

### 2.2 权限分级
| 角色 | 权限范围 | 审批流程 |
|------|----------|----------|
| 普通开发 | 开发环境、非核心代码仓库（写）、测试环境（只读） | 技术经理审批 |
| 高级开发 | 开发环境、核心代码仓库（写）、预发布环境（只读） | 架构师 + 安全组审批 |
| 运维/SRE | 生产环境、云平台管理员权限 | 安全架构组 + CTO 审批 |

### 2.3 最小权限原则
- 生产环境禁止使用 `root` 或 `admin` 账号进行日常操作。
- 数据库访问需通过跳板机（Bastion Host），并开启操作审计日志。
- 每季度由安全组进行一次权限审计，回收冗余权限。

## 3. 代码与版本控制安全

### 3.1 代码仓库管理
- 所有源代码必须托管在公司自建 GitLab（`gitlab.company.com`）或 GitHub Enterprise 中，禁止使用个人公共仓库。
- 仓库权限分为：Owner、Maintainer、Developer、Reporter。核心业务仓库（如支付、用户数据）仅允许 Maintainer 以上角色合并代码。
- 禁止在代码中硬编码密码、API Key、Token、证书等敏感信息。必须使用密钥管理服务（如 HashiCorp Vault 或 AWS Secrets Manager）。

### 3.2 代码审查与扫描
- 所有 Merge Request（MR）必须至少通过 **2 名 Reviewer** 批准后方可合并。
- 每次 MR 提交后，自动触发静态代码扫描工具（如 SonarQube、Checkmarx），安全漏洞评级为 **Critical** 或 **High** 的 MR 禁止合并。
- 第三方依赖库必须经过安全审核，禁止使用已知漏洞版本（CVE 评分 ≥ 7.0 的库立即替换）。

### 3.3 敏感信息泄露防范
- 使用 `git-secrets` 或 `truffleHog` 对提交内容进行预检查。
- 若发现敏感信息已提交至仓库，需立即执行以下步骤：
  1. 通知安全组并锁定仓库。
  2. 使用 `git filter-branch` 或 BFG Repo-Cleaner 删除历史记录。
  3. 更换所有泄露的密钥和 Token。

## 4. 环境与基础设施安全

### 4.1 环境隔离
- 开发、测试、预发布、生产环境必须物理或逻辑隔离。
- 生产环境禁止直接使用公网 IP 暴露服务，必须通过 API Gateway 或负载均衡器（如 Nginx、AWS ALB）对外暴露。
- 环境间网络策略需遵循白名单规则，默认禁止所有流量。

### 4.2 容器与 Kubernetes 安全
- 所有 Docker 镜像必须使用公司内部 Harbor 仓库（`harbor.internal.company.com`）进行管理。
- 容器运行不得使用 `privileged` 模式，且需设置 `readOnlyRootFilesystem: true`。
- Kubernetes 集群必须启用 RBAC 和 NetworkPolicy，禁止使用默认命名空间（`default`）部署业务服务。
- 每两周进行一次容器镜像漏洞扫描（使用 Trivy 或 Clair），修复高危漏洞后方可上线。

### 4.3 日志与监控
- 所有服务器、容器和 API 必须开启操作日志记录，保留时间不少于 **180 天**。
- 日志至少包括：用户 ID、操作时间、请求源 IP、操作内容。
- 集成 SIEM 系统（如 Splunk、ELK Stack），对异常行为（如暴力登录、数据批量导出）进行实时告警。

## 5. 数据安全与隐私保护

### 5.1 数据分类分级
| 等级 | 定义 | 示例 | 保护要求 |
|------|------|------|----------|
| L1-公开 | 可对外公开 | 产品介绍、技术博客 | 无特殊要求 |
| L2-内部 | 仅限内部使用 | 非核心代码、内部报告 | 加密存储，禁止外发 |
| L3-机密 | 核心资产 | 源代码库、数据库密码 | 加密传输+存储，访问需审批 |
| L4-绝密 | 法律/金融敏感数据 | 用户身份证、银行卡号 | 脱敏处理，仅特定人员可接触 |

### 5.2 敏感数据处理
- 生产数据库中涉及个人隐私信息（PII，如手机号、邮箱、地址）必须进行脱敏处理后方可用于开发或测试环境。
- 脱敏规则示例（Python 脚本）：

```python
import re

def mask_phone(phone: str) -> str:
    """手机号中间4位脱敏"""
    return re.sub(r'(\d{3})\d{4}(\d{4})', r'\1****\2', phone)

def mask_email(email: str) -> str:
    """邮箱名脱敏"""
    name, domain = email.split('@')
    masked_name = name[0] + '***' + name[-1] if len(name) > 2 else name[0] + '***'
    return f"{masked_name}@{domain}"
```

- 数据导出必须审批，且通过加密通道（SFTP/HTTPS）传输。

## 6. 应急响应与安全意识

### 6.1 安全事件分级与响应
| 级别 | 定义 | 响应时间 | 处理流程 |
|------|------|----------|----------|
| P0-紧急 | 数据泄露、服务全量瘫痪 | 15 分钟内 | 成立应急小组，直接上报 CTO |
| P1-严重 | 核心服务中断、高危漏洞 | 30 分钟内 | 安全组牵头，技术经理配合 |
| P2-一般 | 非核心服务异常、低危漏洞 | 2 小时内 | 所属团队自行处理，安全组跟进 |

### 6.2 安全意识培训
- 所有新员工在入职 **1 周内** 完成《研发安全必修课》在线培训（包含钓鱼邮件识别、密码安全、数据保护）。
- 每季度组织一次安全攻防演练（Red Team vs Blue Team）。
- 每年进行一次全员信息安全考试，成绩低于 80 分者需补考。
