## 1. 目的与范围

本规范适用于所有业务系统（核心交易、用户中心、支付平台、数据分析）的数据库设计，涵盖MySQL 8.0及TiDB 5.4+。所有新表创建、索引变更、DDL提交必须经过DBA Review。

---

## 2. 表设计规范

### 2.1 命名规范

- 表名：`{业务域}_{模块}_{用途}`，全小写，单词间用下划线分隔，长度不超过32字符。
- 字段名：`{实体}_{属性}`，如`user_id`、`order_status`，禁用保留字（`desc`、`level`、`type`）。
- 索引名：`idx_{表名缩写}_{字段名}`，唯一索引使用`uniq_`前缀。

### 2.2 字段类型选择

| 数据类型 | 适用场景 | 禁止场景 |
|----------|----------|----------|
| `BIGINT UNSIGNED` | 主键、外键、订单号 | 状态码、枚举值 |
| `INT UNSIGNED` | 状态码、年龄、计数 | 超过21亿的ID |
| `VARCHAR(32)` | 用户名、手机号、邮箱 | 超过256字符的长文本 |
| `DECIMAL(18,4)` | 金额、利率 | 使用FLOAT/DOUBLE存储金额 |
| `DATETIME(3)` | 创建时间、更新时间 | 使用字符串存储时间 |
| `JSON` | 扩展属性、配置参数 | 存储结构化关联数据 |

**强制约束**：
- 所有表必须包含 `id`（BIGINT UNSIGNED AUTO_INCREMENT）、`created_at`（DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3)）、`updated_at`（DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)）三个字段。
- `is_deleted` 使用 `TINYINT(1) DEFAULT 0`，禁用NULL。
- 禁止在单表使用TEXT/BLOB类型超过2个字段，超过必须拆分为附属表。

## 3. 索引设计原则

### 3.1 索引创建规则

1. **唯一性约束优先**：业务上具有唯一性的字段（如用户手机号、订单号）必须建立唯一索引。
2. **最左前缀原则**：复合索引的字段顺序需与查询条件匹配，高频过滤字段放在最左侧。
3. **索引下推**：利用MySQL 8.0的ICP特性，避免回表查询。

### 3.2 索引冗余控制

- 单表索引数量不超过5个（含主键），复合索引不超过3个字段。
- 禁止创建重复索引：如已有`idx_user_status`(user_id, status)，则不再创建`idx_user_id`(user_id)。
- 联合索引中，选择性低的字段（如性别、状态）应放在右侧。

### 3.3 索引示例

```sql
-- 正确示例：用户订单查询索引
CREATE INDEX idx_order_user_date ON orders (user_id, created_at, order_status);

-- 错误示例：选择性低的字段放在最前
-- CREATE INDEX idx_order_status_user ON orders (order_status, user_id);
```

## 4. SQL编写规范

### 4.1 查询优化

- 禁止使用 `SELECT *`，必须显式列出所需字段。
- 禁止在WHERE条件中对索引字段使用函数或隐式转换：
  ```sql
  -- 错误：WHERE DATE(created_at) = '2024-01-01'
  -- 正确：WHERE created_at >= '2024-01-01 00:00:00' AND created_at < '2024-01-02 00:00:00'
  ```
- 分页查询必须使用覆盖索引，大偏移量分页改用游标方式：
  ```sql
  -- 传统分页（禁止，大数据量时性能差）
  SELECT id, name FROM users ORDER BY id LIMIT 100000, 20;

  -- 游标分页（推荐）
  SELECT id, name FROM users WHERE id > 100000 ORDER BY id LIMIT 20;
  ```

### 4.2 批量操作

- 单次INSERT/UPDATE影响行数不超过1000行，超过需分批执行。
- 使用`INSERT ... ON DUPLICATE KEY UPDATE`替代先查后改的操作。

## 5. 分区表与分表策略

### 5.1 分区表使用条件

- 表数据量超过5000万行，或单表占用磁盘空间超过100GB。
- 按时间维度分区，使用RANGE分区，分区键必须为主键的一部分：
  ```sql
  CREATE TABLE order_logs (
      id BIGINT UNSIGNED,
      order_id VARCHAR(32),
      created_at DATETIME(3),
      PRIMARY KEY (id, created_at)
  ) PARTITION BY RANGE (TO_DAYS(created_at)) (
      PARTITION p2024_q1 VALUES LESS THAN (TO_DAYS('2024-04-01')),
      PARTITION p2024_q2 VALUES LESS THAN (TO_DAYS('2024-07-01')),
      PARTITION p2024_q3 VALUES LESS THAN (TO_DAYS('2024-10-01')),
      PARTITION p2024_q4 VALUES LESS THAN (TO_DAYS('2025-01-01'))
  );
  ```

### 5.2 分表路由规则

- 用户表按`user_id % 64`分片，分片键必须参与所有查询。
- 订单表按`order_id`的哈希值取模，分片数建议为2的幂次（如32、64）。

## 6. 变更与审计

### 6.1 DDL变更流程

1. 开发人员提交DDL脚本至GitLab仓库 `db-migration/` 目录。
2. 脚本命名格式：`V{版本号}__{描述}.sql`，如`V1.0.3__add_user_index.sql`。
3. DBA审核内容包括：索引冗余检查、锁表风险、数据迁移影响。
4. 生产环境DDL操作必须在业务低峰期（凌晨02:00-05:00）执行，使用`pt-online-schema-change`或`gh-ost`工具。

### 6.2 性能基线

- 单表查询响应时间P99不超过200ms。
- 索引命中率不低于99.5%（可通过`SHOW INDEX FROM table_name`的Cardinality字段评估）。
- 全表扫描必须触发告警，慢查询日志阈值设置为1s。

## 7. 附录：常见反模式

| 反模式 | 说明 | 正确做法 |
|--------|------|----------|
| 使用UUID作为主键 | 随机插入导致页分裂，性能下降30% | 使用自增BIGINT主键 |
| 索引字段包含NULL | MySQL对NULL值处理特殊，影响索引效率 | 设置NOT NULL或DEFAULT值 |
| 冗余存储计算字段 | 如`total_amount = price * quantity` | 使用视图或应用层计算 |
| 大字段加索引 | TEXT/BLOB字段无法加前缀索引 | 使用ES或全文检索 |
