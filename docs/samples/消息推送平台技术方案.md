## 1. 背景与目标

当前业务系统（订单、支付、社交）依赖独立的消息推送模块，存在重复开发、连接管理混乱、消息丢失等问题。为统一推送能力，降低运维成本，设计此平台。

**核心目标**：  
- 支持日推送量 10亿 条  
- 消息送达率 ≥ 99.9%  
- 端到端延迟 ≤ 500ms（99分位）  
- 兼容 iOS/Android/Web/Server 四种通道

## 3. 核心流程设计

### 3.1 推送流程

1. **业务方调用**：POST `/api/push/send`，携带 `{app_id, user_id, payload, priority}`  
2. **API Gateway**：校验签名（HMAC-SHA256），限流（令牌桶 10k/s per app），转发给 Core Engine  
3. **Core Engine**：
   - **Router**：根据 `user_id` 查询用户在线状态（Redis Set），获取当前连接的 Connection Manager Node IP
   - **Filter**：检查用户黑名单、消息有效期（TTL ≤ 24h）、重复消息（基于 payload hash 去重，窗口 5s）
   - **Merge**：相同用户、相同通道的消息合并为一条 batch（减少网络开销）
4. **Connection Manager**：通过 gRPC stream 将消息推送到客户端

### 3.2 离线消息处理

- 若用户离线，消息写入 Kafka topic `offline_messages`
- 用户上线时，Connection Manager 从 Kafka 拉取未消费消息（最多 100 条/次）
- 离线消息保留 7 天后自动删除（通过 Kafka 的日志清理策略）

### 3.3 消息去重机制

```go
// 去重示例代码（Go）
type DedupCache struct {
    store map[string]time.Time // key: payloadHash, value: firstSeen
    mu    sync.Mutex
}

func (d *DedupCache) IsDuplicate(payload []byte) bool {
    hash := sha256.Sum256(payload)
    key := hex.EncodeToString(hash[:])
    d.mu.Lock()
    defer d.mu.Unlock()
    if _, exists := d.store[key]; exists {
        return true
    }
    d.store[key] = time.Now()
    // 5秒后自动清理
    go func() {
        time.Sleep(5 * time.Second)
        d.mu.Lock()
        delete(d.store, key)
        d.mu.Unlock()
    }()
    return false
}
```

## 4. 关键配置参数

### 4.1 Connection Manager 配置

```yaml
# config.yaml
server:
  port: 9090
  max_connections: 100000
  read_timeout: 30s
  write_timeout: 10s

kafka:
  brokers: ["node1:9092", "node2:9092", "node3:9092"]
  topic: "offline_messages"
  consumer_group: "connection_group_1"
  message_retention_hours: 168

redis:
  addr: "redis-cluster:6379"
  password: "push_redis_2023"
  pool_size: 50

target_metrics:
  max_latency_ms: 500
  min_success_rate: 99.9
```

### 4.2 限流策略

| 维度 | 限制 | 超限处理 |
|------|------|----------|
| 每个 App 每秒 | 10,000 条 | 返回 429 Too Many Requests |
| 每个用户每秒 | 100 条 | 丢弃并记录日志 |
| 每个 Connection Node | 100,000 连接 | 拒绝新连接，触发扩容 |

### 4.3 通道适配参数

| 通道 | 最大消息大小 | 超时时间 | 重试次数 | 备注 |
|------|-------------|---------|---------|------|
| WebSocket | 64KB | 5s | 3 | 支持二进制帧 |
| APNs | 4KB | 10s | 2 | 需 JWT 认证 |
| FCM | 4KB | 10s | 2 | 使用 OAuth 2.0 |
| MQTT | 256KB | 30s | 1 | QoS 1 |
| SSE | 无限制 | 60s | 0 | 单向推送 |

## 5. 部署与运维

### 5.1 部署拓扑

- **Push Core Engine**：3 个实例，Kubernetes Deployment，replicas=3，资源请求 4C/8G  
- **Connection Manager**：按区域部署，上海 5 节点，北京 3 节点，均使用 DaemonSet  
- **Kafka**：3 节点集群，每节点 4T SSD，保留 7 天数据  
- **Redis**：6 节点 Cluster，3 主 3 从，用于在线状态缓存

### 5.3 应急预案

| 故障类型 | 触发条件 | 自动化处理 | 人工介入 |
|----------|---------|------------|---------|
| Connection Node 宕机 | 心跳超时 30s | 自动将连接迁移至其他节点 | 重启节点 |
| Kafka 集群不可
