## 一、事件概述

**事件等级**：P0（核心服务中断）

**影响范围**：2025年3月12日 14:32 ~ 14:56，持续约24分钟。线上`user-api`集群对外部请求的响应接口出现大规模`429 Too Many Requests`错误。波及用户约120万，涉及订单查询、登录鉴权、商品浏览等核心业务。

**损失评估**：预计影响订单转化约3000单，并导致部分客户端出现超时重试风暴，间接拉高了下游`order-db`集群的CPU负载至95%。

## 三、根因分析

### 3.1 直接原因

在当天14:00进行的例行配置更新中，运维人员将`user-api`集群的限流策略从**基于IP的全局限流**变更为**基于用户ID的本地计数限流**。修改后的配置文件中，`limit_req_zone`的key错误地使用了`$arg_user_id`（URL参数），而非经过身份验证后的`$http_x_user_token`。

由于大量请求的`user_id`参数为空或为默认值（如`-1`），导致所有空值请求被合并到同一个限流桶中。当并发量超过单个桶的速率（10 req/s）时，网关立即对所有空`user_id`的请求返回429。

### 3.2 根本原因

- **配置评审缺失**：本次限流策略变更未经过SRE或安全团队的Code Review，直接由运维组在`staging`环境测试后，未经充分压测即灰度上线。
- **测试覆盖不足**：`staging`环境的测试数据中，所有测试用户ID均为合法值，未模拟`user_id`为空或异常的边界情况。
- **监控盲区**：原有的告警规则只监控`5xx`和`4xx`总错误率，未针对`429`特定状态码设置独立告警。导致实际错误发生1分钟后才通过`5xx`间接告警发现。

### 3.3 相关配置示例

**错误配置（`/etc/nginx/rate_limiter.conf`）**：

```nginx
# 错误：使用未经校验的URL参数
limit_req_zone $arg_user_id zone=user_api_limit:10m rate=10r/s;

server {
    location /api/v1/ {
        limit_req zone=user_api_limit burst=20 nodelay;
        proxy_pass http://user-api-backend;
    }
}
```

**正确配置（回滚后的版本）**：

```nginx
# 正确：使用经过身份验证的Header
limit_req_zone $http_x_user_token zone=user_api_limit:10m rate=1000r/s;

server {
    location /api/v1/ {
        limit_req zone=user_api_limit burst=200 nodelay;
        proxy_pass http://user-api-backend;
    }
}
```

| order-db CPU | 45% | 95% | 48% |
| 登录成功率 | 99.9% | 12.5% | 99.8% |

### 4.2 客户端影响

部分未实现重试退避机制的Android客户端版本（v3.2.1以下）在收到429后，以1秒间隔持续重试，导致用户侧出现白屏和登录失败弹窗。iOS客户端因使用了指数退避策略，受影响程度较轻。

## 六、总结

本次事故是由于限流配置中key的选择错误，导致合法请求被误伤。暴露了配置变更流程、测试覆盖和监控体系三方面的短板。后续将通过流程加固、自动化测试和灰度机制，杜绝同类问题再次发生。

**最终结论**：事故定性为“人为配置错误”，非系统设计缺陷。责任人已进行一对一辅导，并完成安全培训。
