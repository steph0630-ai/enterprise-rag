## 1. 事件概述

2025年3月12日 14:23 UTC，监控系统告警通知核心日志服务 `log-collector` 出现异常，数据写入失败。经排查发现，日志存储服务器 `/var/log/application/` 所在分区（挂载点 `/data`）磁盘空间使用率达到 100%，导致新产生的业务日志无法写入，累计约 2.3GB 的日志数据（覆盖时间段 14:15-14:23）丢失。

## 3. 根因分析

### 3.1 直接原因

日志存储服务器 `log-store-03` 的 `/data` 分区磁盘空间耗尽。具体配置如下：

```
# df -h /data
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1       500G  500G     0 100% /data

# du -sh /data/logs/application/*
4.2G    /data/logs/application/biz
1.8G    /data/logs/application/error
493G    /data/logs/application/payment-service   <-- 异常
0.8G    /data/logs/application/access
```

`payment-service` 日志目录在 14:10-14:20 期间暴涨 493GB，占用了整个分区的 98.6%。

### 3.2 根本原因

`payment-service` v3.2.1 版本于 2025-03-12 13:50 上线，代码变更中引入了以下缺陷：

```java
// payment-service/src/main/java/com/example/payment/PaymentProcessor.java
// 问题代码：在循环中错误地持续打印堆栈信息
while (retryCount < MAX_RETRIES) {
    try {
        processPayment(order);
        break;
    } catch (NetworkException e) {
        // BUG: 忘记添加日志级别控制，且没有限速
        log.error("Payment processing failed for order: {}", order.getOrderId(), e);
        retryCount++;
    }
}
```

该代码在每次网络重试时都打印完整堆栈跟踪，且重试间隔仅 100ms，导致在 10 分钟内产生了约 493GB 的日志。

### 3.3 系统性原因

1. **日志轮转策略失效**：`log4j2.xml` 配置的滚动策略基于文件大小（100MB）和时间（每小时），但在磁盘写满时无法自动触发清理。
2. **磁盘监控阈值过低**：告警阈值设为 90%，但未配置自动清理脚本。从 90% 到 100% 仅需约 2 分钟（基于 220MB/min 的写入速率）。
3. **无写入限速机制**：日志框架（Logback）未配置 `SizeBasedTriggeringPolicy` 之外的写入速率限制。
4. **代码审查遗漏**：上线前 CR 未发现此循环日志打印问题。

## 6. 改进措施

### 6.1 日志系统优化

在 `logback-spring.xml` 中增加以下配置：

```xml
<!-- 写入速率限制：每分钟最多 100MB -->
<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
    <discardingThreshold>0</discardingThreshold>
    <queueSize>512</queueSize>
    <appender-ref ref="FILE" />
    <filter class="com.example.filter.RateLimitFilter">
        <maxBytesPerMinute>104857600</maxBytesPerMinute> <!-- 100MB -->
    </filter>
</appender>
```

### 6.2 磁盘监控增强

部署新的监控脚本 `/opt/scripts/disk_cleanup.sh`：

```bash
#!/bin/bash
# 磁盘使用率超过 85% 时自动清理 3 天前的日志
THRESHOLD=85
USAGE=$(df /data | awk 'NR==2 {print $5}' | sed 's/%//')
if [ $USAGE -gt $THRESHOLD ]; then
    find /data/logs/ -name "*.log.*" -mtime +3 -delete
    logger "Disk cleanup triggered: usage was ${USAGE}%, removed logs older than 3 days"
fi
```

## 7. 经验教训

1. **日志写入速率必须监控**：日志系统需要独立于业务系统的磁盘告警，且阈值应更低（例如 70% 告警，80% 自动清理）。
2. **代码审查应关注循环内的日志行为**：任何循环中的 `log.error()` 或 `log.warn()` 都应触发人工审查。
3. **灰度发布的重要性**：`payment-service` v3.2.1 直接全量上线，未经历金丝雀发布，导致问题快速扩散。
4. **日志框架的限速能力**：应默认启用日志写入速率限制，防止代码缺陷导致磁盘写满。
