## 2. 根因分析

### 2.1 直接原因

主库 `db-master-01` 在 14:20 左右执行了一次批量数据清理操作：

```sql
-- 清理 90 天前的过期订单
DELETE FROM orders WHERE created_at < '2024-04-13' LIMIT 50000;
```

该操作产生大量 binlog 事件，导致主库的 Dump 线程发送 binlog 到从库时出现积压。从库 `db-slave-02` 的 SQL 线程因 `innodb_flush_log_at_trx_commit` 配置为 `2`（异步刷盘），未能及时应用这些事件，造成延迟。

### 2.2 根本原因

1. **缺乏大事务监控**：批量 DELETE 未拆分小批次执行，单条 SQL 影响 50000 行记录，生成 1.2GB binlog。
2. **从库刷盘策略不当**：`innodb_flush_log_at_trx_commit=2` 虽提升了从库写入性能，但牺牲了数据一致性保障能力。
3. **读写分离架构缺陷**：应用层通过 `@Transactional(readOnly=true)` 自动路由到从库，但未设置 `stale_connection_handling`，导致在延迟期间读取到过期数据。

## 3. 修复过程

### 3.1 数据一致性修复

使用 `pt-table-sync` 工具将主库数据同步到从库：

```bash
# 修复 orders 表差异
pt-table-sync --execute \
  --databases=order_db \
  --tables=orders \
  --sync-to-master h=db-slave-02,u=repair,p=***,P=3306 \
  --charset=utf8mb4 \
  --verbose

# 验证修复结果
pt-table-checksum \
  --databases=order_db \
  --tables=orders \
  h=db-master-01,u=checksum,p=***,P=3306
```

### 3.2 延迟恢复

手动触发从库加速应用 binlog：

```sql
-- 临时提升从库并行复制能力
STOP SLAVE SQL_THREAD;
SET GLOBAL slave_parallel_workers = 8;
START SLAVE SQL_THREAD;

-- 监控延迟
SELECT NOW() - INTERVAL Seconds_Behind_Master SECOND AS estimated_sync_time;
```

## 4. 整改措施

### 4.1 短期措施（24小时内）

| 措施 | 负责人 | 状态 |

| 将从库 `innodb_flush_log_at_trx_commit` 改为 `1` | 张伟 | 已完成 |

| 设置应用层读写分离超时阈值 `spring.datasource.hikari.validation-timeout=3000` | 赵敏 | 已完成 |

### 4.2 长期措施（2周内）

1. **批量操作改造**：所有 DELETE/UPDATE 操作必须使用 `LIMIT 1000` 分批执行，由代码审计工具强制检查。

   示例代码：
   ```python
   def batch_delete_orders(cutoff_date, batch_size=1000):
       while True:
           deleted = execute_sql(
               "DELETE FROM orders WHERE created_at < %s LIMIT %s",
               (cutoff_date, batch_size)
           )
           if deleted == 0:
               break
           time.sleep(0.1)  # 控制主库压力
   ```

2. **配置从库延迟阈值告警**：当 `Seconds_Behind_Master > 5` 持续 10 秒时，自动切换读流量回主库。

   ```yaml
   # Prometheus alert rule
   groups:
   - name: mysql_replication
     rules:
     - alert: MySQLReplicationLagHigh
       expr: mysql_slave_status_seconds_behind_master > 5
       for: 10s
       labels:
         severity: critical
   ```

3. **引入 ProxySQL 中间件**：实现读写分离和延迟感知路由，配置如下：
   ```sql
   -- 创建从库延迟检查规则
   INSERT INTO mysql_query_rules (rule_id, active, match_pattern, destination_hostgroup, comment)
   VALUES (100, 1, '^SELECT.*', 2, 'Read queries go to slave');
   
   -- 设置从库健康检查间隔
   UPDATE global_variables SET variable_value='1000' WHERE variable_name='mysql-monitor_interval';
   ```

## 5. 经验教训

- **避免大事务**：任何影响超过 1000 行的 DML 操作必须拆分为小批次执行，并设置事务超时时间（`lock_wait_timeout=10`）。
- **从库配置需平衡**：`innodb_flush_log_at_trx_commit=1` 虽牺牲部分写入性能，但可避免数据不一致风险。
- **读写分离需兜底**：业务层必须实现降级逻辑，当从库延迟过高时自动切换到主库读取关键数据。
