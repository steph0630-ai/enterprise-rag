## 1. 概述

为保证代码库的可持续维护性、降低技术债务、提升团队协作效率，特制定本规范。所有团队成员在提交代码（Pull Request, PR）前，必须遵循以下标准进行自我审查，并按要求编写提交信息（commit message）。本规范适用于 Git 工作流中的 `feature`、`bugfix`、`hotfix` 分支合并至 `develop` 及 `main` 分支的场景。

## 2. 提交信息规范

### 2.1 格式要求

所有 commit message 必须遵循以下结构：

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**：必填，表示提交类型，详见 2.2 节。
- **scope**：选填，表示影响范围（如模块名、服务名、文件路径）。
- **subject**：必填，简短描述（不超过 50 字符），使用祈使句，首字母小写，末尾不加句号。
- **body**：选填，详细描述，与 subject 之间空一行。解释“为什么修改”及“如何修改”。
- **footer**：选填，用于标注 Breaking Changes 或关联 Issue 编号（如 `Closes #123`）。

### 2.2 提交类型定义

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(auth): add OAuth2 login endpoint` |
| `fix` | Bug 修复 | `fix(parser): handle null input in date parsing` |
| `docs` | 文档变更 | `docs(readme): update API usage example` |
| `style` | 代码格式（不影响逻辑） | `style(utils): reformat imports with isort` |
| `refactor` | 重构（不新增功能、不修复 bug） | `refactor(cache): extract cache key builder` |
| `perf` | 性能优化 | `perf(db): add index on user_email column` |
| `test` | 测试相关 | `test(api): add integration test for /users` |
| `chore` | 构建、CI/CD、依赖更新 | `chore(deps): bump flask from 2.3.0 to 2.4.1` |

### 2.3 示例

```
feat(payment): add Stripe webhook handler

- Implement `handle_webhook` function to verify signature
- Add `PaymentEvent` model to store raw events
- Handle `checkout.session.completed` event for order fulfillment

Closes #456
```

## 3. 代码审查标准

### 3.1 审查前检查清单（提交者自查）

提交 PR 前，开发者必须确认以下事项均已完成：

- [ ] 代码在本地通过 `pytest` 全部测试（`pytest --cov --tb=short`）
- [ ] 无死代码、无 `print` 语句（仅限调试用）
- [ ] 已添加或更新单元测试，覆盖新增逻辑
- [ ] 已运行代码风格检查：`flake8 --max-line-length=100`
- [ ] 已运行类型检查：`mypy --strict`
- [ ] 已编写或更新 API 文档（OpenAPI 注释）

### 3.2 审查者检查清单

审查者在 Code Review 过程中，必须逐一检查以下维度：

#### 3.2.1 功能正确性
- 代码逻辑是否与需求文档一致？
- 边界条件是否处理？（如空列表、None 值、极端输入）
- 异常路径是否覆盖？（如网络超时、数据库连接失败）

#### 3.2.2 代码质量
- 函数/方法职责是否单一？（遵循 Single Responsibility Principle）
- 命名是否清晰？变量名、函数名、类名是否自解释？
- 是否存在重复代码？是否可提取公共方法或工具类？
- 是否过度设计？（如过早抽象、不必要的设计模式）

#### 3.2.3 安全性
- 用户输入是否经过验证和清理？（防止 SQL 注入、XSS）
- 敏感信息（密码、API Key）是否硬编码？
- 是否使用参数化查询而非拼接 SQL 字符串？

#### 3.2.4 性能
- 是否存在 N+1 查询问题？
- 是否在循环中执行数据库查询或外部 API 调用？
- 是否使用缓存（如 Redis）合理？

#### 3.2.5 可测试性
- 关键逻辑是否可单元测试？（避免依赖全局状态）
- 是否引入了 mock 或 stub 难以处理的副作用？

### 3.3 禁止原则

以下情况必须拒绝 PR，并打回修改：

1. **包含未解决的 TODO 或 FIXME 注释**（除非有 Issue 跟踪且明确标注）
2. **测试覆盖率下降**（新增代码单元测试覆盖率 < 80%）
3. **引入新的严重安全漏洞**（如将密码明文存储）
4. **提交信息不符合规范**（缺少 type 或 subject 为空）

## 4. 工具集成

### 4.1 Git Hooks

在项目根目录 `.githooks/` 下部署以下 hook，强制检查 commit message 格式：

```bash
#!/bin/bash
# .githooks/commit-msg
# 检查 commit message 是否符合 Angular 规范

commit_msg_file=$1
commit_msg=$(cat "$commit_msg_file")

pattern="^(feat|fix|docs|style|refactor|perf|test|chore)(\(.+\))?: .{1,50}$"

if ! echo "$commit_msg" | grep -qE "$pattern"; then
    echo "ERROR: Commit message does not follow the required format."
    echo "Format: <type>(<scope>): <subject>"
    echo "Example: feat(auth): add login endpoint"
    exit 1
fi
```

在项目根目录执行以下命令启用 hook：

```bash
git config core.hooksPath .githooks
```

### 4.2 CI/CD 集成

在 GitHub Actions 或 GitLab CI 中，使用以下配置自动执行审查检查：

```yaml
# .github/workflows/code-review.yml
name: Code Review Checks
on: [pull_request]
jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: pip install flake8 mypy pytest
      - name: Lint check
        run: flake8 --max-line-length=100 .
      - name: Type check
        run: mypy --strict src/
      - name: Run tests
        run: pytest --cov=src/ --cov-fail-under=80
```

## 5. 附则

- 本规范由技术架构组维护，每季度修订一次。
- 对于违反规范的情况，由 PR 审查者打回并要求修改；累计违反 3 次以上，由团队负责人进行约谈。
- 如有争议（如规范未覆盖的场景），由技术架构组仲裁。
