## 1. 故障概述

2024年3月15日14:32至15:18，订单核心服务（order-svc）发生大规模超时故障，导致用户无法提交订单、查询订单列表。影响范围覆盖**华北、华东、华南**所有生产环境，涉及**订单创建、支付回调、订单查询**三个核心API。故障等级评定为**P0**。

**核心指标：**
- 故障持续时间：46分钟
- 影响订单数：约18,500 笔
- 用户错误率峰值：72.3% (正常 < 0.5%)
- 经济损失估算：约￥120万元 (基于平均客单价)

## 3. 根因分析

### 3.1 直接原因

后台数据迁移脚本 `data_migrator.py` 在 `order_detail` 表上执行了 `ALTER TABLE order_detail ADD COLUMN batch_id int NOT NULL DEFAULT 0;`。该表数据量约 1.2 亿行，DDL 操作持有了 **metadata lock**，导致所有后续查询（包含 `SELECT`、`UPDATE`、`INSERT`）全部阻塞。

### 3.2 深层原因

1. **缺少 DDL 操作规范**：后台迁移脚本未使用 `pt-online-schema-change` 等在线DDL工具，直接在高峰期对核心表执行 DDL。
2. **长事务未监控**：当时存在一个业务长事务（由用户A的支付回调失败重试导致），该事务持续了 **12分钟** 未提交，导致 `metadata lock` 无法被释放，最终引发全局阻塞。
3. **连接池配置缺陷**：order-svc 使用的 HikariCP 连接池，`max-lifetime` 设置为 30分钟，`idle-timeout` 设置为 10分钟。当数据库连接被阻塞时，连接池无法及时回收和重建新连接，导致服务端线程持续等待。
4. **熔断降级缺失**：订单服务未对数据库查询异常配置熔断降级策略，导致故障发生时所有请求都尝试连接数据库，进一步加剧了连接池耗尽。

## 5. 改进措施

### 5.1 短期措施 (已完成)

| 序号 | 措施 | 责任人 | 完成日期 |
|---|---|---|---|
| 1 | 下线该数据迁移脚本，禁止在业务高峰期手动执行 DDL | 张伟 | 2024-03-15 |
| 2 | 调整 HikariCP 连接池参数：`max-lifetime=180000` (3分钟)，`idle-timeout=60000` (1分钟) | 李雷 | 2024-03-15 |
| 3 | 增加长事务监控告警：MySQL `trx_idle_seconds > 300` 触发 P1 告警 | 韩梅梅 | 2024-03-16 |
| 4 | 为 order-svc 核心接口添加 Resilience4j 熔断器，当错误率达到 50% 时快速失败 | 李雷 | 2024-03-16 |

### 5.2 中期措施 (计划中)

| 序号 | 措施 | 责任人 | 预计完成 |
|---|---|---|---|
| 1 | 上线 DDL 审批流程：所有生产环境 DDL 必须通过工单系统申请，并使用 gh-ost 在线工具执行 | 王刚 | 2024-04-01 |
| 2 | 实现数据库连接池自动扩缩容：当连接使用率超过 80% 时自动扩容 50% | 张伟 | 2024-04-15 |
| 3 | 优化长事务：在业务代码中减少事务范围，对支付回调等关键路径添加事务超时控制 (`@Transactional(timeout = 30)`) | 李雷 | 2024-04-10 |
| 4 | 升级监控体系：增加数据库 `metadata lock` 实时检测告警，并自动发送到 SRE 值班群 | 韩梅梅 | 2024-04-20 |

## 6. 附录

### 6.1 命令参考

**检查当前阻塞的 metadata lock:**
```bash
mysql -h [host] -u root -p -e "
SELECT 
    p1.id AS blocking_pid,
    p1.user AS blocking_user,
    p1.time AS blocking_time,
    p2.id AS waiting_pid,
    p2.user AS waiting_user,
    p2.time AS waiting_time,
    p2.info AS waiting_query
FROM information_schema.processlist p1
JOIN performance_schema.metadata_locks ml1 ON p1.id = ml1.owner_thread_id
JOIN performance_schema.metadata_locks ml2 ON ml1.object_schema = ml2.object_schema 
    AND ml1.object_name = ml2.object_name 
    AND ml1.lock_status = 'GRANTED' 
    AND ml2.lock_status = 'PENDING'
JOIN information_schema.processlist p2 ON p2.id = ml2.owner_thread_id;
"
```

**KILL 阻塞进程 (谨慎使用):**
```sql
-- 先获取阻塞进程 ID，然后执行
KILL 45;
-- 如果无法释放，可能需要 KILL 持有长事务的进程
SHOW ENGINE INNODB STATUS\G;
```
