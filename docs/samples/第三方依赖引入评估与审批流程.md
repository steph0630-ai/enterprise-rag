## 1. 目的与适用范围

为确保第三方依赖引入不影响系统稳定性、安全性及合规性，特制定本流程。  
**适用范围**：公司所有产品线、基础设施及内部工具中引入的第三方开源或商业依赖（包括但不限于 npm、Maven、PyPI、Go Modules、Docker 镜像等）。

---

## 2. 角色与职责

| 角色           | 职责描述                                                     |
|----------------|--------------------------------------------------------------|
| 开发工程师     | 发起引入请求，提供依赖基本信息及必要性说明                   |
| 架构评审组     | 评估依赖对架构兼容性、性能及维护性的影响                     |
| 安全与合规组   | 执行 CVE 扫描、许可证合规检查                                |
| 基础设施团队   | 负责依赖缓存、镜像仓库及自动化扫描环境维护                   |
| CTO / 技术 VP  | 审批高风险或高成本依赖的引入                                 |

## 3. 评估流程

### 3.1 申请阶段

开发工程师需在内部 Jira 工单中创建 **Dependency Request** 类型任务，并填写以下字段：

- 依赖名称及版本号（如：`com.google.guava:guava:32.0.1-jre`）
- 依赖来源（Maven Central / npm Registry / 自建仓库）
- 功能描述（解决什么业务问题）
- 替代方案分析（至少列出 2 个替代依赖及弃用理由）

### 3.2 自动化扫描阶段

工单创建后，触发 Jenkins Pipeline 自动执行以下检查：

```bash
# 示例：使用 OWASP Dependency-Check 进行 CVE 扫描
dependency-check --scan ./pom.xml --format HTML --out ./reports/dep-report.html

# 使用 FOSSA 或 Trivy 进行许可证合规检查
trivy fs --severity HIGH,CRITICAL --exit-code 1 --ignorefile .trivyignore ./pom.xml
```

**扫描报告需包含**：
- 已知 CVE 数量及严重级别（Critical / High / Medium）
- 许可证类型（如 MIT、Apache 2.0、GPL 等）及合规性标记
- 依赖传递性分析（Transitive Dependencies）

### 3.3 人工评审阶段

#### 3.3.1 架构评审

架构评审组评估以下维度，评分规则如下表：

| 评分维度       | 权重 | 评分标准（1-5分）                                          |
|----------------|------|------------------------------------------------------------|
| 模块间耦合度   | 30%  | 1分：强耦合；3分：可隔离；5分：零耦合                      |
| API 稳定性     | 25%  | 1分：预览版；3分：稳定版；5分：长期支持版                  |
| 社区维护活跃度 | 20%  | 1分：近6个月无提交；3分：季度更新；5分：月度更新           |
| 替代方案成熟度 | 25%  | 1分：无替代；3分：有备选但功能弱；5分：有成熟替代已内部使用 |

**总分 >= 3.5 分** 方可进入下一环节。

#### 3.3.2 安全与合规评审

安全组检查以下内容：

- 依赖是否包含已知恶意代码（如 `npm audit` 检测到 `malicious` 类型）
- 许可证是否与公司开源政策冲突（禁止 GPLv3、AGPL 等强传染性许可证）
- 依赖是否来自受制裁地区或组织（参考公司 IP 控制清单）

**示例：许可证白名单**

```json
{
  "allowed": ["MIT", "Apache-2.0", "BSD-2-Clause", "ISC"],
  "conditional": ["LGPL-2.1", "MPL-2.0"], // 需法务单独审批
  "blocked": ["GPL-3.0", "AGPL-3.0", "BUSL-1.1"]
}
```

### 3.4 最终审批

| 依赖风险等级 | 审批人           | 审批条件                                                       |
|--------------|------------------|----------------------------------------------------------------|
| 低风险       | 技术经理         | 自动化扫描通过，架构评分 >= 3.5，安全合规无异常                |
| 中风险       | 架构评审组长     | 除上述条件外，需提供性能压测报告（QPS >= 2000）                |
| 高风险       | CTO / 技术 VP    | 需提交《依赖引入豁免申请》，说明业务不可替代性及风险缓解措施 |

## 4. 紧急引入豁免流程

当线上故障修复、安全漏洞应急响应需要紧急引入依赖时，可申请豁免：

1. **紧急通道**：在 Jira 中标记 `Critical` 优先级，并附上故障链接
2. **快速评估**：安全组在 2 小时内完成 CVE 扫描（仅限 Critical 级别）
3. **事后补审**：引入后 3 个工作日内补全完整评估流程，否则将触发自动回滚

**注意**：同一依赖每年最多使用 2 次紧急豁免，超出需 CTO 特批。

## 6. 违规处理

- **未流程引入依赖**：首次警告并强制回滚，重复违规记入绩效扣分（-2 分/次）
- **引入恶意依赖**：立即启动安全事件响应（SIR），相关责任人需提交书面说明
- **许可证违规**：法务部介入，视情节严重性处以 1-3 个月禁止发布权限
